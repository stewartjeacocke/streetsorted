# Implementation Plan: Prototype Landing Page

**Branch**: `008-prototype-landing-page` | **Date**: 2026-10-04 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/008-prototype-landing-page/spec.md`

## Summary

Add a root landing page that introduces Street Sorted as a fly-tipping reporting prototype, explains
the reporting journey, and links residents to the existing `/report` entry point. Author the page as
the `index.hbs` Handlebars template using the existing shared layout, then render it to final
`index.html` during the asset build. Express will serve the generated HTML through its existing static-asset middleware;
no browser JavaScript, client routing, or request-time landing-page rendering is introduced.

## Technical Context

**Language/Version**: TypeScript targeting ES2024; Node.js 26

**Primary Dependencies**: Express 5, Handlebars 4

**Storage**: N/A; the landing page has fixed content and creates no persistent or session data

**Testing**: Node.js built-in test runner with Supertest; Playwright browser tests; ESLint; Prettier

**Target Platform**: Node.js web server serving HTML to modern desktop and mobile browsers

**Project Type**: Single server-rendered web service

**Performance Goals**: The root entry page is a single pre-rendered static document; it must preserve
the existing report-flow performance and let first-time visitors identify its purpose and call to
action within 30 seconds, as specified by SC-001.

**Constraints**: Preserve progressive enhancement; do not add an SPA, client-side routing, browser
Handlebars runtime, or generated JavaScript template. Render the Handlebars template to final HTML
at build time; reuse the current layout and stylesheet; expose no resident data, credentials, or
submission claim from the landing page.

**Scale/Scope**: One public root document, one new private Handlebars template, asset-build and
development-startup updates, plus focused unit and request-level coverage. The existing `/report`
flow, API, sessions, and report-submission behavior remain unchanged.

## Implementation Design

1. Add `index.hbs` beside the existing report templates. It will invoke `layout` and contain
   semantic introductory content: prototype status, purpose, three reporting steps, preparation
   guidance, and one ordinary `/report` anchor with a dedicated primary-action treatment that remains
   understandable without styles.
2. Extend the asset-build module to read `layout.hbs` and `index.hbs`, register the layout as a
   Handlebars partial, render `index.hbs` with fixed context, and write the rendered result
   to `index.html` in the selected public destination after copying ordinary public assets.
3. Keep runtime report templates private under the server-view output. The `index.hbs` source is likewise
   private; only the final public HTML document is published.
4. Update development startup to generate the same public asset output before Express begins serving
   static files. Production retains `npm run build` as the producer of the generated root document.
5. Add focused tests for final HTML artifact generation, source-template non-publication, root-page
   delivery through configured static middleware, shared layout markers, required explanatory text,
   the `/report` primary link, primary-action treatment, and semantic document order. Preserve all
   current report-flow behavior and test coverage.
